# Fork note: Garmin vs Garmin Health Data — data model

This document describes how **classic Garmin** (`provider_type` / `source` / `source_provider` = `garmin`) and **Garmin Health Data** (`garmin_health_data`) write into Sparky Postgres, what GHD adds on top, and how isolation / duplication works.

Ops setup for the GHD sidecar lives in [14.fork-garmin-health-data.md](./14.fork-garmin-health-data.md).

Snapshot figures below were taken from a local `docker-compose.dev` database after both providers had successfully synced overlapping ranges (classic roughly mid‑July → Aug 21; GHD April → Aug 21). Counts will differ per environment.

---

## 1. Mental model

| Layer | Classic Garmin | Garmin Health Data (GHD) |
|---|---|---|
| Provider type | `garmin` | `garmin_health_data` |
| Sidecar | `sparkyfitness-garmin` (Python Connect client) | `sparkyfitness-ghd` (PyPI `garmin-health-data` warehouse) |
| Deep archive | Not kept (fetch → map → discard) | Per-user SQLite under `/data/{user_id}/` (~39 tables) |
| Postgres role | Map Connect JSON into product tables | Project training-useful subset into the **same** product tables, tagged with a different source |
| Unique strengths | Nutrition diary, workout definitions / strength sets, some Connect-only summary fields | Multi-year gap-fill, FIT-backed activities, denser intraday history, GHD job provenance tables |

**Isolation rule:** every projected product row is tagged with either `garmin` or `garmin_health_data`. The two integrations never overwrite each other’s rows. They *can* both store a row for the same calendar day or the same Garmin activity id — that is **parallel provenance**, not a primary-key clash.

## 2. Shared product tables (both can write)

These tables already existed for wearables. Both providers use them; uniqueness always includes the source tag where relevant.

### 2.1 `daily_health_metrics`

**Uniqueness:** `UNIQUE (user_id, entry_date, source_provider)`

One day can therefore have **two** rows (one per provider). Upserts only collide within the same `source_provider`.

| Field family | Classic `garmin` | GHD `garmin_health_data` |
|---|---|---|
| Identity | `source_provider = 'garmin'` | `source_provider = 'garmin_health_data'` |
| Steps / floors | Yes (`total_steps`, floors) | Yes (steps often from SQLite `steps` sum; floors when present) |
| Calories | `active_calories`, `bmr_calories` common | Calories rarely filled today (projection leaves them null) |
| Distance | `total_distance_meters` from Connect | Not projected currently |
| Intensity | `exercise_minutes` (Connect intensity) | `moderate_intensity_minutes`, `vigorous_intensity_minutes` from `training_load` |
| RHR / stress / body battery | Yes | Yes (stress averaged from samples; BB high/low/charge/drain) |
| VO₂ / fitness age / lactate / hill / endurance / race preds | Often from Connect max-metrics payloads | VO₂ when present in GHD `vo2_max`; race/fitness extras usually absent |
| Training load | `acute_training_load`, `chronic_training_load`, `acwr_ratio`, `weekly_training_load` | Same acute/chronic/acwr from GHD `training_load` (no weekly field yet) |
| Training readiness / recovery | From Connect readiness payloads when present | From GHD `training_readiness` when present |

**Local snapshot (field fill rates):**

| source_provider | rows | steps filled | RHR | VO₂ | readiness | ATL/CTL/ACWR | stress | body battery | active calories |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| `garmin` | 31 | 22 | 21 | 1 | 0 | 31 | 31 | 26 | 31 |
| `garmin_health_data` | 143 | 143 | 19 | 11 | 0 | 142 | 118 | 123 | 0 |

Overlapping calendar days (both sources present): **31** in the local DB. Example: same day can show different `total_steps` (different extractors / clocks) while ATL often matches.

### 2.3 `sleep_entries`

Tagged with `source` (`garmin` | `garmin_health_data`). Primary key is row `id` only — re-sync paths typically **delete-by-source-and-date-range** then re-insert for that provider.

| Aspect | Classic | GHD |
|---|---|---|
| Source tag | `garmin` | `garmin_health_data` |
| Stages | Connect sleep stages when present | GHD `sleep` + `sleep_level` projected into `stage_events` |
| Scores / HRV / SpO₂ overnight | When Connect provides them | When GHD sleep row provides them |

**Local snapshot:** classic 3 nights; GHD 19 nights. Overlapping nights (same `entry_date`, both sources): **3**.

### 2.4 `exercise_entries` (+ related telemetry)

Both create diary activities with:

| Column | Classic | GHD |
|---|---|---|
| `source` | `garmin` | `garmin_health_data` |
| `source_id` | Garmin activity id when available (often null on some classic rows) | Always set to Garmin activity id |
| `notes` | `Garmin Activity: …` | `GHD Activity: …` |
| Details | `activity_details.provider_name = 'garmin'` | `provider_name = 'garmin_health_data'` |
| Laps / GPS / sets | Classic Connect payloads; strength sets when present | GHD FIT-derived laps/GPS when projected |

**GHD-only provenance:** `ghd_activity_map (user_id, garmin_activity_id) → exercise_entry_id` prevents GHD from projecting the same Garmin activity twice.

**Cross-provider activity behaviour (important):**

- Before insert, GHD checks `ghd_activity_map` **and** any existing `exercise_entries` with the same `source_id` for `source IN ('garmin','garmin_health_data')`. If classic already imported that id, **GHD skips**.
- Classic Garmin **does not** check for an existing GHD row. If GHD imported first, classic can still create a second `exercise_entries` row with the same `source_id`.

**Local snapshot:**

| source | rows | distinct `source_id` | null `source_id` |
|---|---:|---:|---:|
| `garmin` | 36 | 5 | 31 |
| `garmin_health_data` | 43 | 43 | 0 |

Cross-source pairs sharing the same Garmin `source_id`: **5** (same physical activity represented twice — once per provider). Within each source, no duplicate `source_id`s.

### 2.5 `custom_measurements` (check-in style)

Classic Garmin maps many Connect summary keys through `garminMeasurementMapping` into custom categories with `source = 'garmin'`.

GHD may write body-composition-style measurements with `source = 'garmin_health_data'` when the sidecar projection includes body composition (often empty if Garmin has no weigh-ins).

**Local snapshot:** 495 classic custom measurement rows (Jul 22–Aug 21); **0** GHD custom measurements (no body-comp in warehouse for this user).

### 2.6 `food_entries` (nutrition)

| | Classic | GHD |
|---|---|---|
| Writes nutrition? | Yes (`source = 'garmin'`) | **No** |

Keep classic Garmin linked if nutrition sync matters. Local snapshot currently had **0** classic food rows for this user (nutrition phase may be empty or not yet completed for the synced window).

## 3. Tables / objects added only for GHD

Created by migration `20260821220000_garmin_health_data_provider.sql` (Tier 1 owner RLS).

### 3.1 Catalog

- `external_provider_types` row: id `garmin_health_data`, display name “Garmin Health Data”, strictly private credentials (`email` / `password` for login only; tokens live in the sidecar).

### 3.2 `ghd_sync_runs`

Audit of keep-alive / manual extract+project runs: `user_id`, `provider_id`, `started_at`, `finished_at`, `status`, date range, `error_summary`, `stats` JSONB.

### 3.3 `ghd_activity_map`

| Column | Purpose |
|---|---|
| `user_id` | Owner |
| `garmin_activity_id` | Garmin Connect activity id (PK with user) |
| `exercise_entry_id` | Projected `exercise_entries.id` (nullable if cleared) |
| `last_projected_at` | Last successful projection |

### 3.4 `ghd_history_import_jobs` / `ghd_history_import_weeks`

Chunked “Fill history gaps” job: range, cursor, week counters, per-week `extract_ok` / `project_ok` / status. At most one active (`pending`/`running`/`paused`) job per user.

### 3.5 Sidecar SQLite (not in Postgres)

Examples of warehouse tables that feed projection: `steps`, `heart_rate`, `stress`, `body_battery`, `hrv`, `spo2`, `respiration`, `sleep`, `sleep_level`, `activity`, `training_load`, `training_readiness`, `vo2_max`, `body_composition`, floors, race predictions, etc. Postgres only receives the projected product subset above.

## 4. Overlap vs duplicate — what is guaranteed

### Guaranteed (no destructive overlap)

1. **Different source tags** — classic never updates a `garmin_health_data` row and vice versa.
2. **Daily health / samples uniqueness includes `source_provider`** — same day/metric can exist twice without PK violation; re-sync upserts only the matching provider.
3. **GHD activity map** — GHD will not create a second GHD row for the same Garmin activity id.
4. **GHD respects classic activities** — if classic already stored `source_id = <garmin activity id>`, GHD skips that activity.

### Not guaranteed (semantic duplicates possible)

1. **Same calendar day, two daily/sleep/sample rows** (one per provider) when both synced overlapping ranges — expected parallel provenance. UI / Training consumers must choose a preferred source (Training currently treats both as Garmin-family).
2. **Same Garmin activity as two `exercise_entries`** if **GHD ran first (with UTC diary dates)** and classic synced later — classic historically did not consult `ghd_activity_map`. Classic now skips when the Garmin `source_id` already exists for either provider. GHD projection now emits **local** start times (via `timezone_offset_hours`) so `entry_date` matches classic `startTimeLocal`.
3. **Numeric disagreement** on shared days (e.g. steps) — different pipelines / time zones / partial days; ATL often still aligns.
4. **Distance units** — GHD stores metres on `exercise_entries.distance`; some classic rows may store kilometres from Connect. Same workout can look “similar but scaled” (e.g. `2783` vs `2.8`).

#### Timezone skew (historical)

GHD SQLite `activity.start_ts` is UTC-naive. Before the local-time projection fix, Sparky used that UTC stamp for `entry_date`, while classic used Connect `startTimeLocal`. Evening workouts then appeared as **same duration/distance, adjacent dates** (often +1 day on GHD), and dedupe-by-date missed them even though `source_id` matched.

Example from local Docker after both synced:

| Garmin activity id | GHD date/time | Classic date/time | Duration |
|---|---|---|---|
| 23856609520 (soccer) | 2026-08-05 01:33 | 2026-08-04 19:33 | 52.71 min |
| 24055640269 (run) | 2026-08-21 00:52 | 2026-08-20 18:52 | 18.73 min |

Re-projecting GHD activities (or deleting the UTC-dated GHD rows and re-syncing) plus relying on classic’s skip-if-already-imported cleans this up going forward. Existing duplicate pairs may need a one-time cleanup.

### Practical guidance

| Goal | Recommendation |
|---|---|
| Deep wellness + FIT history for Training | Prefer **GHD** + “Fill history gaps”, then daily keep-alive |
| Nutrition / Connect workout definitions | Keep **classic Garmin** |
| Avoid double activities in the diary | Prefer syncing **classic activities only for windows GHD has not covered**, or add a future classic-side skip when `ghd_activity_map` / GHD `source_id` already exists |
| Reporting “one number per day” | Query with an explicit preferred `source_provider` (or coalesce GHD over classic) |

## 5. Local verification queries

Useful checks after both providers sync:

```sql
-- Row counts by source
SELECT 'daily_health_metrics' AS tbl, source_provider, COUNT(*) 
FROM daily_health_metrics
WHERE source_provider IN ('garmin','garmin_health_data') GROUP BY 2
UNION ALL
SELECT 'sleep_entries', source, COUNT(*) FROM sleep_entries
WHERE source IN ('garmin','garmin_health_data') GROUP BY 2
UNION ALL
SELECT 'exercise_entries', source, COUNT(*) FROM exercise_entries
WHERE source IN ('garmin','garmin_health_data') GROUP BY 2
UNION ALL
SELECT 'health_metric_samples', source_provider, COUNT(*) FROM health_metric_samples
WHERE source_provider IN ('garmin','garmin_health_data') GROUP BY 2;

-- Same calendar day present for both daily providers
SELECT COUNT(*) AS overlapping_daily_days
FROM daily_health_metrics d1
JOIN daily_health_metrics d2
  ON d1.user_id = d2.user_id AND d1.entry_date = d2.entry_date
 AND d1.source_provider = 'garmin_health_data'
 AND d2.source_provider = 'garmin';

-- Same Garmin activity id imported by both (semantic duplicate activities)
SELECT g.source_id, g.entry_date AS ghd_day, c.entry_date AS garmin_day
FROM exercise_entries g
JOIN exercise_entries c
  ON g.user_id = c.user_id AND g.source_id = c.source_id
WHERE g.source = 'garmin_health_data' AND c.source = 'garmin';

-- Within-source activity id duplicates (should be 0 for GHD)
SELECT source, source_id, COUNT(*)
FROM exercise_entries
WHERE source IN ('garmin','garmin_health_data') AND source_id IS NOT NULL
GROUP BY 1, 2 HAVING COUNT(*) > 1;
```

## 6. Summary diagram

```text
Garmin Connect account
        │
        ├─► sparkyfitness-garmin  ──fetch──► map (source='garmin')
        │         │
        │         ├─ daily_health_metrics
        │         ├─ health_metric_samples
        │         ├─ sleep_entries
        │         ├─ exercise_entries (+ activity_details, sets, …)
        │         ├─ custom_measurements
        │         └─ food_entries                    ← classic only
        │
        └─► sparkyfitness-ghd  ──extract──► SQLite warehouse
                  │
                  └─ project (source='garmin_health_data')
                        ├─ daily_health_metrics
                        ├─ health_metric_samples
                        ├─ sleep_entries
                        ├─ exercise_entries (+ laps/GPS when present)
                        ├─ custom_measurements (body comp when present)
                        ├─ ghd_activity_map
                        ├─ ghd_sync_runs
                        └─ ghd_history_import_*
```

Rows are isolated by source tag. Overlapping days/activities are **side-by-side**, not merged. Within each provider, upserts / GHD activity map keep re-syncs from multiplying identical provider-owned rows.
